## Recommended flow if Banodoco owns the hosted page

1. CLI asks the Hivemind broker for a short-lived request and keeps the high-entropy polling secret locally.
2. CLI opens `https://www.banodoco.ai/connect/?request=<opaque-request>`; the page stores only that opaque request in `sessionStorage`, then starts Discord OAuth against the shared Supabase project. Never place the poll secret in the URL.
3. OAuth returns to the fixed `/connect/` callback. The page completes the Supabase session (PKCE or the pinned browser SDK), clears the request URL, and POSTs the request capability plus the browser's Supabase access token to a Hivemind broker approval endpoint.
4. The broker verifies the Supabase JWT/server-side identity mapping and records only the approved identity. The page displays approval; the CLI polls with its local secret and redeems once, atomically receiving the plaintext Hivemind key.

The Banodoco static page needs a pinned client implementation (either vendored `supabase-js` or a carefully tested direct PKCE/Auth REST flow), explicit broker CORS for the exact Banodoco origin, and a Supabase Auth redirect allowlist entry. The page itself never gets service-role credentials or a contributor key.

## Host adjudication

Recommend Banodoco as the browser host, with a pinned Supabase browser SDK rather than hand-written OAuth. Keep all broker/credential authority in Hivemind. After Discord login the page must display the requesting machine/code and require an explicit approval action before POSTing approval; OAuth completion alone must not silently authorize a machine. Do not replace the existing Hivemind GitHub link merely to expose this flow; CLI-generated links suffice for this scope.
